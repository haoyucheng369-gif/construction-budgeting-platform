# 报价与预算服务实施计划

## 交付目标

计划周期约两周，按 10 个工作日组织任务，另外保留约 4 个自然日用于环境问题、联调和修复。天数是任务顺序与时间分配建议，实际进度以 [TODO.md](TODO.md) 的验收结果为准。

完成一条可运行的 ERP 报价流程：报价编辑 → 成本组成重算 → 读取预算基准 → 更新预算差额和毛利 → 页面实时更新。同时支持从资源库改价触发受影响报价重算。

T01 已完成：Sales 分层宿主与基础设施已验证；业务用例从 T02 开始。架构与业务口径见 [architecture-decisions.zh-CN.md](architecture-decisions.zh-CN.md)。

## 范围

保留 .NET 8、React/TypeScript/React Query、Clean/Hexagonal、DDD、CQRS、MediatR、MassTransit/RabbitMQ、PostgreSQL、SQL Server 只读、SignalR、Docker Compose。

四个业务服务按顺序接入：Sales、Library、Compositions、Budget。每个服务独立运行。Sales 保留 Clean Architecture 四层；Compositions 在 T04.3 / T05 按六边形的业务核心、输入/输出端口与适配器组织；Library、Budget 延续简单分层。不用把每层和每个概念都拆成独立项目。

先介绍 Sales 骨架并完成一个小用例，再在进入 Compositions 时对照说明端口与适配器的边界。两者统一遵循依赖向内，沿用相同的事件与数据所有权约定；不增加服务、业务流程或额外排期阶段。详细取舍见架构决策第 8 节。

页面只保留项目选择、资源价格表、报价工作台。工作台包含报价行、成本明细、预算差额、毛利和计算状态。配方和初始资源通过种子数据提供，不开发配方编辑器。

本期不安排 Kubernetes、云部署、CI/CD、鉴权/权限、多副本、Redis、Selenium 平台、完整契约升级流程、性能专项、前端独立业务计算、自动定价、审批、采购、库存或发票。后端输出权威计算结果，前端负责编辑与呈现。

## 技术实现深度

| 技术 | 本期达到的程度 |
| --- | --- |
| DDD | Sales 的 Quote 聚合、QuoteLine、Money、Quantity 与明确业务约束；其他服务按复杂度保持简单 |
| Clean / Hexagonal | Sales 使用 Clean 四层，Compositions 明确实现输入/输出端口与适配器；业务规则不依赖数据库和消息总线，使用测试替身验证核心并单独检查真实适配器 |
| CQRS / MediatR | 分开读写用例，用处理器串起业务；不增加独立读服务或 Event Sourcing |
| 微服务 | 四个宿主可分别启动与重启，至少一条真正跨进程事件链 |
| MassTransit / RabbitMQ | 消费与发布、有限重试、错误日志/队列、持久化去重和版本保护 |
| 两个数据库 | PostgreSQL 保存业务及计算结果；SQL Server 只读提供预算基准 |
| React Query / SignalR | REST 获取结果，收到通知后定向刷新，重连后重新查询 |
| Docker | 基础设施先容器运行；最后将应用服务一起纳入 Compose |

事务性 Outbox 是时间允许时的首选增强项，不作为首个业务闭环的前置条件。未实现前，记录数据库提交成功但消息未发送的故障窗口，保留按最新状态重新触发计算的操作入口；不宣称消息绝不丢失。

## 排期控制

优先级按业务闭环决定：能正确保存与重算 > 跨服务传播 > 页面联动 > 额外工程增强。

如果落后，先减少 UI 修饰、通用抽象和辅助页面，继续使用预置配方与数据；不增加新基础设施。完成 T01–T10 后才考虑可选项。范围变更需要同步 TODO 和架构决策，不能因为外部材料提到某技术就自动纳入本期。

## 完成标准

- 从空的本地数据库按文档初始化并启动。
- 能创建报价、增删行、修改数量及销售价格，重新打开后数据正确。
- 数量变化和资源价格变化分别通过服务间事件更新成本、预算差额和毛利。
- SQL Server 应用账号无法写入；缺失预算显示未配置。
- 两个窗口查看同一报价，其中一个修改后，另一个获取新结果。
- 并发修改、重复消息和旧结果有基本保护；计算失败不冒充成功。
- 关键规则测试与选定集成检查通过，剩余限制明确记录。
