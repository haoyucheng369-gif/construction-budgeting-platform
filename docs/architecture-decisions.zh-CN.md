# 架构与业务决策

本文件记录当前实现约定。功能完成情况以 [TODO.md](TODO.md) 为准；本文中的设计不代表代码已经实现。

## 1. 交付边界

本期约两周，完成报价、资源成本、预算差额、毛利与实时更新。采用 Docker Compose 本地运行，不包含 Kubernetes、云部署、CI/CD、鉴权/权限、多副本或 Redis。

采用 .NET 8，不自动升级框架。已引入的依赖版本在下表及锁文件中固定；其他包在对应任务引入时锁定。React/TypeScript/React Query 为前端；服务内使用 MediatR，服务间使用 MassTransit/RabbitMQ。

## 2. 服务边界与依赖

| 服务 | 负责内容 | PostgreSQL 所有权 |
| --- | --- | --- |
| Sales / Vente | 项目、草稿报价、销售金额、最终成本/毛利视图、SignalR | `sales` |
| Library | 材料和人工资源、成本单价、资源版本 | `library` |
| Compositions | 预置配方、资源/报价输入投影、成本快照与计算修订号 | `compositions` |
| Budget | 读取预算基准、计算差额、记录计算结果 | `budget_projection` |

四个服务独立进程运行，逐个接入，不额外创建项目管理或通知服务。SignalR 放在 Sales；客户端通过 REST 读写，通过通知知道数据过期。

服务内部依赖指向业务层。Domain 保持业务规则，Application 编排用例，Infrastructure 提供存储与消息适配器，API 处理 HTTP/Hub。采用文件夹或必要的程序集边界，不为每个概念创建一个项目。

跨服务共享仅限集成契约，不共享聚合、DbContext 或可变业务状态。CQRS 分离读写职责，不引入 Event Sourcing。

## 3. 数据库

- PostgreSQL 为读写存储，以独占 schema、账号和迁移区分服务。不得跨服务表查询、Join、写入或使用跨服务事务。
- SQL Server 保存既有预算基准。独立初始化脚本建表和填充数据，运行中的应用使用只读账号。
- Budget 的计算结果、处理记录保存到 PostgreSQL 的 `budget_projection`；SQL Server 不承接这些写入。
- 一个 PostgreSQL 数据库的共享运行维护依赖属于当前部署边界，不声称各服务数据库可独立故障或扩容。
- 项目没有对应预算基准时显示“未配置”，不能用零预算代替。已有基准不会随报价变更自动修改。

## 4. 业务规则

- 每个项目一份草稿报价，支持添加/删除行、修改数量和销售单价。固定资源与配方由种子数据初始化；资源成本单价可编辑。
- 使用 EUR，不含税；工程量与资源消耗按线性关系计算；不处理损耗、阶梯价、审批、历史锁价或自动定价。
- 数量大于零，销售价和资源成本不小于零，允许负毛利。
- 行销售额 = 工程量 × 销售单价，逐行到分后求和。
- 成本分项 = 工程量 × 每单位资源消耗 × 资源成本单价，逐分项到分后求和。
- 预计毛利 = 销售额 − 预计成本；毛利率 = 预计毛利 ÷ 销售额；销售额为零时毛利率为空。
- 预算差额 = 预算基准 − 预计成本，负数表示超预算。
- C# 金额采用 decimal，舍入使用 MidpointRounding.AwayFromZero；中间计算不提前舍入，最终金额保留两位小数。
- 前端使用后端返回的业务金额，仅格式化与编辑输入，不自行实现完整成本或毛利计算。
- 资源成本变化影响所有引用该资源的草稿。固定销售价保持不变，成本与毛利更新。

### 固定验收样例

刷漆每 m² 使用一份材料和一份人工；材料初始成本 5 EUR，人工 7 EUR，预算基准 1,300 EUR。各行是按顺序修改后的状态。

| 状态 | 销售额 | 预计成本 | 预计毛利 | 毛利率 | 预算差额 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 数量 100，销售价 20 | 2,000 | 1,200 | 800 | 40% | 100 |
| 数量改为 120 | 2,400 | 1,440 | 960 | 40% | -140 |
| 销售价改为 22 | 2,640 | 1,440 | 1,200 | 45.45% | -140 |
| 材料成本改为 7 | 2,640 | 1,680 | 960 | 36.36% | -380 |

## 5. 事件流

报价输入变化：Sales 保存 → `QuoteInputsChanged` → Compositions 成本重算 → `CompositionCosted` → Budget 读取基准并计算 → `BudgetImpactCalculated` → Sales 保存最终视图 → SignalR → React Query 定向刷新。

资源改价：Library 保存 → `ResourcePriceChanged` → Compositions 更新资源价格投影、重算受影响报价 → 同一条 Budget / Sales 下游链。

Compositions 通过事件持有所需输入，不在计算时读取其他服务的表。初始资源、配方、项目与预算标识由可重复执行的种子/初始化流程关联。

事件携带业务标识、MessageId、CorrelationId 和输入版本。QuoteVersion 标识报价输入；ResourceVersion 标识资源价格；CompositionRevision 是每份报价的计算修订号。价格变化并不一定改变 QuoteVersion，因此不能只凭报价版本防止旧结果覆盖。

Compositions 持久化最新输入并用事务/并发控制生成计算修订号。下游拒绝旧报价版本和旧修订号。固定配方使初版不需要额外处理配方变更版本。

Sales 应用计算结果不会重新发布报价输入事件，避免形成循环。结果带来源版本；页面在等待计算时标记旧值，不把它当成最新值。

## 6. 本期可靠性与限制

必做：输入验证、乐观并发、持久化重复消息保护、原子版本比较、有限重试、带关联标识的错误记录、明确的计算状态，以及按最新输入重新触发计算的入口。

业务状态和消费处理记录在同一个本地事务中保存。发布失败必须能定位，不能只吞掉错误或把计算标记为已完成。重算操作生成新的处理请求标识，同时保留业务输入版本，避免被旧的去重记录直接跳过。

事务性 Outbox 为可选增强。未实现时存在数据库提交与消息发布之间的故障窗口，包括下游消费者更新结果后发布下一条消息的窗口；需要人工重新触发计算来恢复，不能宣称自动可靠投递或恰好一次处理。失败/长时间未完成在页面可见。

SignalR 采用单实例、项目分组；通知后定向重新查询。断线重连后重新入组并补读最新状态；保存后的计算可短期轮询兜底。它不承担持久化结果或可靠消息投递。

并发修改带当前版本，冲突返回明确响应（例如 HTTP 409）并提示刷新。暂不自动合并多人编辑。

## 8. 设计依据与取舍

### 从业务变化确定职责

报价数量变化与资源成本变化是两个入口。它们都影响成本和毛利，但数据的管理方不同：Sales 管销售数量与售价，Library 管资源单价，Compositions 管资源配方与消耗规则，Budget 管与既有预算基准的比较。

先确定这些规则和所有权，再决定接口、消息和数据库访问。需要能够说明每一份数据由谁维护、变化后谁负责反应，不能以“有四种技术”作为拆四个服务的理由。

### 为什么同时提 Clean、六边形和 DDD

Clean Architecture 强调依赖指向内部业务；六边形架构强调业务通过端口与外部适配器交互。当前方案采用它们相通的原则，不把它们当作两套必须分别安装的框架，也不声称两者在所有细节上完全相同。

DDD 解决的是业务模型与边界。例如报价行不是可以任意写入的数据库记录：数量必须合法，销售金额按统一规则计算，修改必须属于这份报价。Quote 聚合提供业务操作来维护这些约束。

实际分工：Domain 定义业务是否合法、金额如何计算；Application 负责取得报价、调用操作、协调保存；Infrastructure 实现数据库与消息访问；API 处理 HTTP 输入输出。一次更新请求的执行顺序不等于项目引用方向：运行时可以从用例调用数据库适配器，编译时通过内部定义的接口保持依赖向内。

### 为什么先建四层程序集

四个程序集让依赖关系可见并由项目引用约束。Domain 不引用 EF Core、ASP.NET Core 或 RabbitMQ，因此核心规则可以脱离服务器与数据库测试。更换数据访问实现时，不需要改变报价规则。

代价是项目数量和少量接口代码增加。因此只保留必要边界，不给每个类创建抽象，不提前建立通用 Repository、通用服务基类或大量空框架代码。Application 仅在用例需要外部能力时定义端口。

### 为什么 Quote 是聚合而不是每行一个独立入口

初版报价行的生命周期依附报价，修改数量、增删行和维护报价版本有共同的一致性要求。通过 Quote 控制写入可避免在 API、前端、数据库适配器中分别实现不同版本的规则。

代价是整份报价的并发范围较大：两人修改不同的行也可能发生版本冲突。当前以每项目一份小规模草稿为边界，接受此代价，后续只有真实规模需要时再调整。

### 为什么 CQRS、MediatR 与消息总线分开

写入需要加载业务模型并校验，读取只需返回页面所需的数据，所以分开命令与查询。CQRS 在这里不等于两个数据库，也不要求两套部署。

MediatR 提供进程内用例分发入口，让 API 不依赖具体处理器；它不提供跨进程投递和故障恢复。RabbitMQ 负责服务之间的消息传递，MassTransit 负责发布、消费及相关配置。二者处理不同的通信边界。

### 为什么跨服务采用事件以及代价

销售报价的保存不应要求预算服务此刻也可用。事件使下游计算能够在输入保存后独立处理，而不是在一次 HTTP 请求中串联等待所有服务。

代价是报价已保存与全部重算完成之间会有时间差，因此页面必须区分保存状态和计算状态。重复、乱序和故障也需要显式处理；引入总线不会自动带来可靠性。当前未做 Outbox 时仍存在保存与发布之间的窗口，这个限制不会因使用 RabbitMQ 而消失。

### 为什么四个服务仍需要控制规模

独立服务对应当前选择的业务所有权，并满足跨进程事件通信的架构目标；微服务本身并不保证比单体更简单或更快。四个服务会增加启动、调试、数据复制和联调成本。

因此本期保持固定配方、少量业务页面、单实例和一个 Compose 环境，不再拆独立通知或项目服务。如果某个边界后续只产生转发而没有独立规则，需要重新评估该边界，而不是为了保留服务数量继续增加层次。

### 为什么区分预算基准与预算影响结果

既有预算基准属于外部只读数据。重新计算得到的预计成本和预算差额是本系统的派生结果，应保存到自己可写的存储，不能通过改写基准来让预算跟随报价变化。

PostgreSQL 用 schema 隔离数据所有权，是保留两库同时控制部署数量的选择；它仍共享数据库故障和资源竞争范围，不等于每服务一个独立数据库。

### 为什么前端只呈现权威结果

报价、成本和毛利的规则集中在后端，可避免两套算法在舍入、边界条件和版本方面发生分歧。React Query 管理远端数据缓存，SignalR 通知哪些数据需要刷新；两者都不成为最终金额的依据。

这样会牺牲即时本地计算反馈，所以用保存中、计算中、完成/失败状态说明实际进度。先保证结果一致，暂不增加前端计算引擎。

### 为什么先做宿主和环境检查

T01 先确认版本、端口、服务启动和数据库权限，便于把环境问题与之后的业务问题分开定位。健康检查只证明宿主可用；领域模型和业务正确性仍需 T02 之后的测试验证。

Docker Compose 满足本期的本地服务编排需求。Kubernetes、云与鉴权会增加独立工作量，并不改变当前报价计算规则，所以不纳入两周交付。
