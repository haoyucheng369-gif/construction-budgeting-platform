# 架构与业务决策

本文件记录当前实现约定。功能完成情况以 [TODO.md](TODO.md) 为准；本文中的设计不代表代码已经实现。

## 1. 交付边界

本期约两周，完成报价、资源成本、预算差额、毛利与实时更新。采用 Docker Compose 本地运行，不包含 Kubernetes、云部署、CI/CD、鉴权/权限、多副本或 Redis。

采用 .NET 8，不自动升级框架。已引入的依赖版本在下表及锁文件中固定；其他包在对应任务引入时锁定。React/TypeScript/React Query 为前端；服务内使用 MediatR，服务间使用 MassTransit/RabbitMQ。

## 2. 服务边界与依赖

| 服务 | 负责内容 | PostgreSQL 所有权 |
| --- | --- | --- |
| Sales / Vente | 项目、草稿报价、销售金额、最终成本/毛利视图、SignalR | `sales` |
| Library | 材料和人工资源、成本单价、资源版本 | `library` |
| Compositions | 预置配方、资源/报价输入投影、成本快照与计算修订号 | `compositions` |
| Budget | 读取预算基准、计算差额、记录计算结果 | `budget_projection` |

四个服务独立进程运行，逐个接入，不额外创建项目管理或通知服务。SignalR 放在 Sales；客户端通过 REST 读写，通过通知知道数据过期。

服务内部依赖指向业务层。Sales 保留 Domain、Application、Infrastructure、Api 四层的 Clean Architecture 结构；Compositions 按六边形架构明确组织业务核心、输入/输出端口与适配器。Library、Budget 延续简单分层。采用文件夹或必要的程序集边界，不为每个概念创建一个项目；具体对应关系与理由见第 8 节。

跨服务共享仅限集成契约，不共享聚合、DbContext 或可变业务状态。CQRS 分离读写职责，不引入 Event Sourcing。

## 3. 数据库

- PostgreSQL 为读写存储，以独占 schema、账号和迁移区分服务。不得跨服务表查询、Join、写入或使用跨服务事务。
- SQL Server 保存既有预算基准。独立初始化脚本建表和填充数据，运行中的应用使用只读账号。
- Budget 的计算结果、处理记录保存到 PostgreSQL 的 `budget_projection`；SQL Server 不承接这些写入。
- 一个 PostgreSQL 数据库的共享运行维护依赖属于当前部署边界，不声称各服务数据库可独立故障或扩容。
- 项目没有对应预算基准时显示“未配置”，不能用零预算代替。已有基准不会随报价变更自动修改。

## 4. 业务规则

- 每个项目一份草稿报价，支持添加/删除行、修改数量和销售单价。固定资源与配方由种子数据初始化；资源成本单价可编辑。
- 使用 EUR，不含税；工程量与资源消耗按线性关系计算；不处理损耗、阶梯价、审批、历史锁价或自动定价。
- 数量大于零，销售价和资源成本不小于零，允许负毛利。
- 行销售额 = 工程量 × 销售单价，逐行到分后求和。
- 成本分项 = 工程量 × 每单位资源消耗 × 资源成本单价，逐分项到分后求和。
- 预计毛利 = 销售额 − 预计成本；毛利率 = 预计毛利 ÷ 销售额；销售额为零时毛利率为空。
- 预算差额 = 预算基准 − 预计成本，负数表示超预算。
- C# 金额采用 decimal，舍入使用 MidpointRounding.AwayFromZero；中间计算不提前舍入，最终金额保留两位小数。
- 前端使用后端返回的业务金额，仅格式化与编辑输入，不自行实现完整成本或毛利计算。
- 资源成本变化影响所有引用该资源的草稿。固定销售价保持不变，成本与毛利更新。

### 固定验收样例

刷漆每 m² 使用一份材料和一份人工；材料初始成本 5 EUR，人工 7 EUR，预算基准 1,300 EUR。各行是按顺序修改后的状态。

| 状态 | 销售额 | 预计成本 | 预计毛利 | 毛利率 | 预算差额 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 数量 100，销售价 20 | 2,000 | 1,200 | 800 | 40% | 100 |
| 数量改为 120 | 2,400 | 1,440 | 960 | 40% | -140 |
| 销售价改为 22 | 2,640 | 1,440 | 1,200 | 45.45% | -140 |
| 材料成本改为 7 | 2,640 | 1,680 | 960 | 36.36% | -380 |

## 5. 事件流

报价输入变化：Sales 保存 → `QuoteInputsChanged` → Compositions 成本重算 → `CompositionCosted` → Budget 读取基准并计算 → `BudgetImpactCalculated` → Sales 保存最终视图 → SignalR → React Query 定向刷新。

资源改价：Library 保存 → `ResourcePriceChanged` → Compositions 更新资源价格投影、重算受影响报价 → 同一条 Budget / Sales 下游链。

Compositions 通过事件持有所需输入，不在计算时读取其他服务的表。初始资源、配方、项目与预算标识由可重复执行的种子/初始化流程关联。

事件携带业务标识、MessageId、CorrelationId 和输入版本。QuoteVersion 标识报价输入；ResourceVersion 标识资源价格；CompositionRevision 是每份报价的计算修订号。价格变化并不一定改变 QuoteVersion，因此不能只凭报价版本防止旧结果覆盖。

Compositions 持久化最新输入并用事务/并发控制生成计算修订号。下游拒绝旧报价版本和旧修订号。固定配方使初版不需要额外处理配方变更版本。

Sales 应用计算结果不会重新发布报价输入事件，避免形成循环。结果带来源版本；页面在等待计算时标记旧值，不把它当成最新值。

## 6. 本期可靠性与限制

必做：输入验证、乐观并发、持久化重复消息保护、原子版本比较、有限重试、带关联标识的错误记录、明确的计算状态，以及按最新输入重新触发计算的入口。

业务状态和消费处理记录在同一个本地事务中保存。发布失败必须能定位，不能只吞掉错误或把计算标记为已完成。重算操作生成新的处理请求标识，同时保留业务输入版本，避免被旧的去重记录直接跳过。

事务性 Outbox 为可选增强。未实现时存在数据库提交与消息发布之间的故障窗口，包括下游消费者更新结果后发布下一条消息的窗口；需要人工重新触发计算来恢复，不能宣称自动可靠投递或恰好一次处理。失败/长时间未完成在页面可见。

SignalR 采用单实例、项目分组；通知后定向重新查询。断线重连后重新入组并补读最新状态；保存后的计算可短期轮询兜底。它不承担持久化结果或可靠消息投递。

并发修改带当前版本，冲突返回明确响应（例如 HTTP 409）并提示刷新。暂不自动合并多人编辑。

## 8. 设计依据与取舍

### 从业务变化确定职责

报价数量变化与资源成本变化是两个入口。它们都影响成本和毛利，但数据的管理方不同：Sales 管销售数量与售价，Library 管资源单价，Compositions 管资源配方与消耗规则，Budget 管与既有预算基准的比较。

先确定这些规则和所有权，再决定接口、消息和数据库访问。需要能够说明每一份数据由谁维护、变化后谁负责反应，不能以“有四种技术”作为拆四个服务的理由。

### 为什么同时提 Clean、六边形和 DDD

Clean Architecture 强调依赖指向内部业务；六边形架构强调业务通过端口与外部适配器交互。当前方案采用它们相通的原则，不把它们当作两套必须分别安装的框架，也不声称两者在所有细节上完全相同。

DDD 解决的是业务模型与边界。例如报价行不是可以任意写入的数据库记录：数量必须合法，销售金额按统一规则计算，修改必须属于这份报价。Quote 聚合提供业务操作来维护这些约束。

Sales 的实际分工：Domain 定义业务是否合法、金额如何计算；Application 负责取得报价、调用操作、协调保存；Infrastructure 实现数据库与消息访问；API 处理 HTTP 输入输出。一次更新请求的执行顺序不等于项目引用方向：运行时可以从用例调用数据库适配器，编译时通过内部定义的接口保持依赖向内。

### 服务内部结构选择：Sales 用 Clean，Compositions 用六边形

2026-09-19 确定：Sales 保留现有 Clean 四层骨架；Compositions 在 T04.3 / T05 按明确的端口与适配器结构实现。Library、Budget 延续简单分层，不新增其他架构变体。这是本项目的组织选择，不代表两种架构互斥，也不代表外部系统已采用相同目录结构。

Compositions 同时接收报价输入变化和资源价格变化，独立完成成本计算、存储并发布结果，输入与输出边界清晰。将消息处理与成本规则隔离后，业务用例可以由消息适配器或测试直接驱动。Sales 则保留已有结构，避免无业务收益的重建。

| 职责 | Sales 的 Clean 组织方式 | Compositions 的六边形组织方式（计划） |
| --- | --- | --- |
| 业务规则 | Domain 中的报价聚合和值对象 | 核心领域模型中的配方、消耗与成本规则 |
| 用例与入口 | Application 中的命令、查询及处理器 | 核心应用用例与输入端口，接收与传输技术无关的输入 |
| 外部能力约定 | Application 中的持久化、发布接口 | 核心定义的输出端口：读取/保存输入及成本、发布计算结果 |
| 技术实现 | Api 与 Infrastructure | 输入适配器（消息消费者）、输出适配器（PostgreSQL、消息发布）、宿主装配 |

资源价格从 5 改为 7 的计划调用路径：RabbitMQ/MassTransit 消费适配器转换消息 → 调用更新资源价格并重算的输入端口 → 应用用例调用成本领域规则 → 经输出端口保存状态、发布结果 → PostgreSQL 和消息适配器执行外部操作。适配器依赖核心约定，核心不依赖适配器实现；领域规则不接触 MassTransit 消费上下文或 EF Core 类型。MediatR 仍只负责进程内分发，不替代端口职责。

端口表达业务操作或所需能力，不是网络端口，也不要求为每个操作额外创建一个接口。输入端口可以由明确的命令/用例契约表达。目录与程序集在 T04.3 根据实际边界确定，不预建大量空项目；区别必须体现在依赖和可替换边界，不能仅更换文件夹名称。

代价是两种内部结构增加导航与维护成本。因此统一事件契约、版本/幂等约定、日志关联、错误处理及测试习惯；跨服务通信、数据所有权、DDD 与 CQRS 范围保持不变。端口隔离本身不解决提交与发布的故障窗口，仍遵守第 6 节的可靠性限制。

验证安排：T04.3 检查核心与适配器的引用方向，并通过真实消息与数据库验证输入适配器；T05 使用内存或测试替身实现输出端口，直接驱动用例验证成本规则，再补充真实适配器集成检查。替身测试不代替数据库事务和消息投递验证。

实施顺序：先介绍 Sales 骨架并完成一个小用例，再进入 Compositions 时逐项对照。Compositions 的上述结构与用例均为计划；Sales 领域模型的完成情况以 TODO 为准。

### 为什么先建四层程序集

四个程序集让依赖关系可见并由项目引用约束。Domain 不引用 EF Core、ASP.NET Core 或 RabbitMQ，因此核心规则可以脱离服务器与数据库测试。更换数据访问实现时，不需要改变报价规则。

代价是项目数量和少量接口代码增加。因此只保留必要边界，不给每个类创建抽象，不提前建立通用 Repository、通用服务基类或大量空框架代码。Application 仅在用例需要外部能力时定义端口。

### 为什么 Quote 是聚合而不是每行一个独立入口

初版报价行的生命周期依附报价，修改数量、增删行和维护报价版本有共同的一致性要求。通过 Quote 控制写入可避免在 API、前端、数据库适配器中分别实现不同版本的规则。

代价是整份报价的并发范围较大：两人修改不同的行也可能发生版本冲突。当前以每项目一份小规模草稿为边界，接受此代价，后续只有真实规模需要时再调整。

### Quote 的最小聚合入口

Sales.Domain 的 `Quotations/Quote.cs` 以非空 Guid Id 标识报价，以非空 ProjectId 关联项目；创建时允许空行集合，总销售额为 0 EUR。它目前表示草稿报价，不增加审批/合同状态机，也不访问数据库校验项目存在性。每项目仅一份草稿的跨报价唯一性要在应用与持久化步骤实现，单个聚合不能保证全系统唯一。

`AddLine(lineId, workItemCode, description, unit, quantity, salesUnitPrice)` 是添加的统一入口：先检查本报价内行 ID 重复，再在内部构造 QuoteLine，计算新总额，最后将行加入私有集合并更新总额。传入值对象可以安全复用，因为它们不可变；不接收外部构造的 QuoteLine，不把同一个行实例附加到多份报价。QuoteLine 的公开构造仍用于独立规则验证，构造并不等于加入报价。

行身份在报价内唯一，定位行时使用 QuoteId + LineId；不同报价允许使用同一个行 ID，各自持有不同实例。工程项代码相同的多行是允许的，例如办公室和走廊分别刷漆。跨服务事件及未来持久化需要保留报价归属，不仅凭 LineId 假定全局唯一。

外部只得到只读包装的 `IReadOnlyList<QuoteLine>`，不能通过强转拿到可修改的底层 List。行和所含值对象当前也只读。总额由聚合保存并在添加时更新，以已舍入的 LineAmount 求和；两行各 0.005 EUR 得到 0.01 + 0.01 = 0.02 EUR，而不是先合计原值再舍入为 0.01。

所有业务校验、行金额计算和总额溢出检查在修改聚合前完成；失败时原有行与总额保持不变。这是内存对象状态的一致性保证，不是数据库事务或多线程并发保证。代价是后续每个修改/删除操作也必须一致地维护行与缓存总额，因此新增行为时需验证相同的不变量。

创建/添加测试覆盖身份、重复行、相同工程项、多报价隔离、只读集合、逐行舍入与失败原子性。修改数量、售价、删除与输入版本见以下各节；数据库并发保护按后续小步骤实现。

### 通过 Quote 修改行数量

`Quote.ChangeLineQuantity(lineId, quantity)` 只在当前报价内查找行，拒绝空 Guid、空 Quantity 或不存在的行。数量的正数约束仍由 Quantity 维护；新旧数量值相等时返回原行，不替换对象或重算总额。

修改时构造新 QuoteLine，沿用原行 Id、工程项、说明、单位和销售单价，重新计算并舍入行金额；新总额 = 旧总额 − 旧行已舍入金额 + 新行已舍入金额。先完成全部计算，再替换集合中的对应位置并更新总额。验证或溢出失败时保持原状态；减少数量、零售价、多次修改遵循同一规则。

替换只读行实例保留了外部不可变边界，业务实体身份仍是原行 ID。代价是调用方持有的旧行引用不会自动更新，应使用返回的新行或重读 Quote.Lines；未来 EF Core 映射/跟踪必须考虑替换行为，目前尚未实现。不同报价即使使用同一个行 ID，也不会互相影响。

本入口是内存业务操作，输入版本遵循下文统一规则，尚无事件或多用户并发控制。测试覆盖数量增减、身份/元数据保留、其他行不变、同值无操作、重复修改后的舍入、零售价、空值/缺失行、行金额与总额溢出及跨报价隔离。

### 通过 Quote 修改销售单价

`Quote.ChangeLineSalesUnitPrice(lineId, salesUnitPrice)` 在当前报价内定位行，保留行 ID、工程项、说明、单位及数量，用新单价构造替换行。复用 QuoteLine 的非负售价检查与先乘后舍入规则；允许零售价，拒绝负数（即使它舍入后可能为零）。空 ID、空 Money、缺失行或金额溢出都在状态修改前失败。

新总额同样按“旧总额 − 旧行金额 + 新行金额”计算，全部成功后才替换只读行实例并更新总额。相同 Money 值为无操作；不同单价即使产生相同行金额，也要保留新的原始单价。数量修改和售价修改始终读取集合中的最新行，避免使用旧引用覆盖另一项修改。

这一入口负责销售金额，不负责成本重算或毛利；输入版本遵循下文统一规则，当前没有消息或持久化。替换实例的取舍与 ChangeLineQuantity 相同。测试覆盖涨价、降价、零价、微小负价拒绝、精度与舍入、同价无操作、金额不变但单价变化、空值/缺失行、溢出、跨报价隔离及与数量修改交错执行。

### 通过 Quote 删除报价行

`Quote.RemoveLine(lineId)` 表达从当前草稿中取消一个工程项。例如刷漆 2000 EUR、地板 3000 EUR 的报价，删除刷漆后保留地板，总额变为 3000 EUR。删除必须由 Quote 同时维护集合与总额，不能直接从外部修改集合。实现读取当前行已舍入的 LineAmount，先计算新总额再删除行，因此先改数量或售价再删除时扣除的是最新金额。

删除最后一行后保留身份不变、总额为零 EUR 的空草稿，仍可继续添加行；不删除整个报价或工程项目。零售价行也可以删除，即使总额不变，工程项集合仍发生变化。

空 Guid 抛出 ArgumentException；当前报价内找不到行时抛出 KeyNotFoundException，均不改变状态。重复删除同样报缺失行，避免将错误行标识静默当作成功；代价是调用方要处理不存在的行，未来 HTTP/消息重试语义在应用边界设计。输入版本遵循下文统一规则，尚无持久化删除或事件。测试验证余下行的顺序/身份、空草稿、零价行、失败不变、修改后最新金额、舍入和跨报价隔离。

### Quote.Version 标识报价输入的变化

Quote 暴露只读的 `long Version`，新空草稿从 1 开始，内部私有 setter 仅供聚合维护。使用简单递增数字表示输入的新旧，不引入时间戳、独立版本值对象或框架依赖；它不是业务审批版本、历史快照或消息 ID。初始值 1 是本系统约定，不是 DDD 的强制规则。

每次成功 AddLine、RemoveLine 或实际改变数量/销售单价，版本恰好加 1；相同数量/同价无操作、校验失败和金额溢出均不递增。免费行增删或改数量、单价变化但舍入金额不变，也属于输入变化；判断依据是输入而非总额。删除到空草稿不重置版本；将数量 100 改成 120 再改回 100，仍记为两次变化。多次领域操作即使将来在一次保存中提交，也可以跨越多个版本，不要求数据库提交一次只加 1。

四个编辑入口都先完成校验、金额计算及 `checked(Version + 1)`，然后更新集合、金额和版本。checked 防止 long 到达上限后回绕，版本计算失败在状态修改之前发生。版本由整份报价拥有，不同报价各自递增；这是输入一致性的边界，代价是未来两人修改不同报价行也可能产生整份报价的版本冲突。

当前实现仅跟踪内存输入版本。计划的持久化路径要保存读取时的版本，并在数据库中原子比较后写入新状态；单纯 Version++ 或应用层先查询再比较都不能阻止并发覆盖。持久化恢复须保留已存版本，不能通过重放 AddLine 意外递增。API/消息版本序列化契约、EF 映射及冲突响应留到对应步骤确定。

未来 QuoteInputsChanged 的 QuoteVersion 对应此输入版本。资源成本变化、收到成本/预算计算结果不会递增报价输入版本；这些结果按来源版本与 CompositionRevision 判断新旧，避免输入事件循环。上述跨服务路径尚未实现。当前测试覆盖初始值、四个操作递增、同值/失败不变、金额不变但输入变化、改回原值、删除到空及报价间独立。

### Quantity 的最小边界

报价行工程量必须大于零，这条规则由 Sales.Domain 中的 `Quotations/Quantity.cs` 集中维护。Quantity 只保存 decimal 数值，允许小数、不提前舍入；计量单位由后续报价行与工程项/配方关联确定，本步不实现单位换算或不同单位间的运算。移除工程项应通过删除报价行表达，不用零数量代替。

采用不可变的 `sealed record` 引用类型：构造函数校验数值，只读 Value 防止创建后绕过校验；按数值比较相等，没有业务 ID。避免使用 struct 的默认零值绕过正数约束。代价是引用类型可能为 null，使用方 QuoteLine 接收 Quantity 时拒绝 null。无计量单位的数值相等不表示不同工程单位可以互换。

验证覆盖正整数、小数及精细工程量（例如 0.0001）的原值保留、零/负数拒绝和数值相等语义。独立领域测试项目只引用 Domain，不需要 ASP.NET Core、数据库或 Docker。

### Money 的金额、币种与舍入边界

Sales.Domain 的 `Quotations/Money.cs` 用不可变 sealed record 表达 decimal Amount 与 Currency；按金额和币种进行值比较，没有独立 ID。本期仅接受标准代码 `EUR`，构造时默认 EUR；显式传入其他币种、空值或非标准大小写会被拒绝，不实现币种转换或多币种运算。

Money 允许正数、零及负数，因为预计毛利与预算差额可能为负；“销售单价不得为负”属于 QuoteLine 的约束，不能放进所有金额共用的构造函数。它是 Sales 内部的值对象，不作为跨服务共享领域模型或消息契约。

构造函数保留 decimal 原值，不自动舍入。`RoundToCents()` 显式返回按两位小数、MidpointRounding.AwayFromZero 舍入的新 Money，原对象不变。例如单价 1.005 EUR × 数量 100 得到行金额 100.50 EUR；若先将单价舍入成 1.01，结果会错误地变成 101 EUR。负中点 -1.005 舍入为 -1.01。

这一选择允许 Money 临时表示尚未舍入的单价或中间结果，代价是最终金额的使用方必须在正确时点调用舍入；QuoteLine 负责乘法和行金额舍入，Quote 按第 4 节规则汇总已舍入行金额。Money 只提供金额表示、币种约束、值相等和舍入方法，不提前增加算术运算符或报价行为；数据库精度及输入上限留到持久化步骤确定。decimal 仍受自身范围与精度限制。

测试覆盖原值保留、零/负数、拒绝不支持的币种、正负舍入中点、原对象不变和值相等，并用单价乘数量的例子验证没有提前舍入；QuoteLine 测试进一步验证实际行金额计算。

### QuoteLine 的身份、计量单位与行金额

Sales.Domain 的 `Quotations/QuoteLine.cs` 表达一条可识别的报价工程项，例如墙面刷漆 100 m²、销售单价 20 EUR/m²、行金额 2000 EUR。它采用 sealed class，具有非空 Guid Id；即使两行内容相同，也可以有不同的行身份，不按全部字段的值相等将其合并。暂不引入通用 Entity 基类或自定义相等运算符，聚合在自己的行集合内通过 Id 识别报价行。

WorkItemCode 用作工程项的稳定关联代码（例如 PAINT），Description 保存显示说明，Unit 保存计量单位代码（例如 m2）；单价表示每个 Unit 的售价，Quantity 表示以同一单位计量的数量。三个字符串必须非空且去除首尾空白。本步不建立工程项目录或跨服务查询，不校验代码是否存在、单位是否与配方匹配，也不进行单位换算；这些关联规则在接入预置工程项与配方时补齐，不能将非空检查当成完整配方校验。

构造时拒绝空 Quantity、空 Money 与负销售单价，允许零售价。行金额在保留原始数量/单价精度的前提下，先相乘，再调用 Money.RoundToCents；LineAmount 只读，不能从外部指定一个与数量/售价不一致的金额。超出 decimal 表示范围时构造失败并抛出 OverflowException，不截断或钳制金额；API 输入上限和错误映射后续确定。

QuoteLine 提供公开构造函数和只读属性，便于独立验证行规则，不提供修改方法或独立仓储。创建对象不等于已加入报价；Quote.AddLine 创建属于该报价的行，维护报价内 ID 唯一性与总额。Quote 的 ChangeLineQuantity 和 ChangeLineSalesUnitPrice 通过相同行 ID 的新只读实例更新数量或售价；RemoveLine 负责移除行并维护总额。输入版本由 Quote 统一维护，报价行没有独立版本。

测试覆盖标准刷漆金额、零售价、小数与中点舍入、输入精度保留、负售价（包括舍入后可能为零的微小负数）、缺失身份/字段、空值、相同工程项不同身份及乘法溢出。本步未接入应用用例、数据库或消息。

### 为什么 CQRS、MediatR 与消息总线分开

写入需要加载业务模型并校验，读取只需返回页面所需的数据，所以分开命令与查询。CQRS 在这里不等于两个数据库，也不要求两套部署。

MediatR 提供进程内用例分发入口，让 API 不依赖具体处理器；它不提供跨进程投递和故障恢复。RabbitMQ 负责服务之间的消息传递，MassTransit 负责发布、消费及相关配置。二者处理不同的通信边界。

### 首个应用用例：修改报价行数量

`Sales.Application/Quotations/ChangeQuoteLineQuantity` 包含命令、处理器和结果 DTO。以刷漆 100 m² 改为 120 m² 为例，命令表达修改意图，携带 QuoteId、LineId、新数量和 ExpectedVersion；处理器负责取得报价、检查版本、调用领域行为、协调保存与返回结果。Quantity 校验、行金额、总额与版本递增仍由 Domain 负责，处理器不复制计算公式。

`IQuoteRepository` 放在 Application，因为当前需求是应用用例取得/保存 Quote，领域模型本身不需要访问存储。接口仅有 GetByIdAsync 与 SaveAsync，不提前建立通用 CRUD 仓储或独立 UnitOfWork 抽象。未来 Infrastructure 实现接口，依赖方向保持向内；本步只有测试替身。代价是需要维护接口契约和适配器测试，替身验证不能代替真实数据库验证。

处理器在读取前拒绝空标识、非正版本，并通过 Quantity 构造函数验证数量；读取后检查请求版本是否等于报价当前版本，连同值请求也拒绝过期版本。找不到报价/行使用 KeyNotFoundException；版本不匹配使用应用层 QuoteConcurrencyException，携带报价标识和期望版本。未来 API 再把这些异常映射为 HTTP 响应，目前尚未实现错误映射。

有效修改后以“修改前版本”调用 SaveAsync，返回 DTO 前等待保存完成。仓储契约要求在同一个原子操作/事务内比较存储版本并保存聚合，保存时版本冲突（包括读取后报价被删除）抛出 QuoteConcurrencyException。应用层预检查只排除已知过期输入，不能防止读取后发生的竞争；数据库实现与并发验证仍在 T02.3。同值操作不调用保存，返回读取到的结果；此结果仍可能随后过期，不承诺锁定当前数据库状态。

保存失败时异常向上传递，不返回成功结果、不自动重试已修改的聚合，也不声称回滚内存对象。仓储必须按工作单元提供聚合，不能让不同请求共享可变 Quote；失败后丢弃该工作单元，下一次重新读取。CancellationToken 从用例传给读写操作；已取消的请求在读取前终止。

命令结果只包含报价/行标识、数量、行金额、总销售额、币种和版本这些只读标量。金额直接取领域模型；不把可变聚合返回给调用方，也不把此应用结果预先认定为最终 HTTP 契约。`AddSalesApplication()` 注册 MediatR 及处理器，当前测试通过作用域内的 ISender.Send 验证分发。API 尚未调用该注册，也未暴露业务路由。

应用测试覆盖成功与原版本保存、免费行有效修改、同值不保存、过期版本、缺失报价/行、非法输入、领域金额溢出、存储故障/冲突传播、取消与实际分发。该入口是 CQRS 的第一个写用例；读取用例见下节，真实仓储、HTTP 和跨进程消息仍按后续小步骤接入。

### 查询报价：独立的读取职责与结果快照

应用层沿用当前命名：请求使用 Command/Query，处理器使用 Handler，返回数据使用 Result/Details，不统一追加 Dto 后缀；类型按用例目录组织，与 Domain 模型区分。

打开报价时只需要展示数据，新增 `Sales.Application/Quotations/GetQuote`，将此用例与修改数量命令分开。GetQuoteQuery 只携带 QuoteId，不要求 ExpectedVersion；GetQuoteHandler 调用已有 IQuoteRepository.GetByIdAsync，返回 GetQuoteResult 和 QuoteLineDetails。查询不调用修改方法或 SaveAsync，不递增版本，也不重新计算金额。

结果复制报价/项目身份、版本、总额、币种及各行的标识、工程项、说明、单位、数量、原始销售单价和已舍入金额。当前整份报价仅支持 EUR，币种放在报价结果上。使用只含标量的行 DTO，并立即生成新数组、以只读集合包装返回；不把聚合、实体引用或延迟 LINQ 枚举交给调用方。因此报价之后被修改或删除行，之前返回的结果仍保持查询时的值。此快照只是一份读取结果，不代表实现了历史版本存储或数据库快照隔离。

本期先复用仓储读取入口，避免为小规模报价建立第二套数据访问接口。代价是读取也要加载完整聚合；未来若有规模或性能依据，可以改成只查询 DTO 所需字段。命令/查询处理器分开即为当前 CQRS 的职责分离，不要求不同数据库或读副本；共享仓储不会把查询变成写用例。

空 ID/null 请求在仓储调用前拒绝，报价不存在抛出 KeyNotFoundException，真实空草稿则返回空行集合和零总额。已取消请求提前终止，CancellationToken 传给读取操作；读取异常向上传递，不伪造空报价。沿用现有 MediatR 程序集注册即可发现新 Handler。测试覆盖字段/顺序、金额精度、空草稿、不改变/保存、返回结果与聚合分离、失败与取消，以及实际查询→修改→查询分发；仍只使用测试仓储，HTTP 与持久化尚未接入。

### 为什么跨服务采用事件以及代价

销售报价的保存不应要求预算服务此刻也可用。事件使下游计算能够在输入保存后独立处理，而不是在一次 HTTP 请求中串联等待所有服务。

代价是报价已保存与全部重算完成之间会有时间差，因此页面必须区分保存状态和计算状态。重复、乱序和故障也需要显式处理；引入总线不会自动带来可靠性。当前未做 Outbox 时仍存在保存与发布之间的窗口，这个限制不会因使用 RabbitMQ 而消失。

### 为什么四个服务仍需要控制规模

独立服务对应当前选择的业务所有权，并满足跨进程事件通信的架构目标；微服务本身并不保证比单体更简单或更快。四个服务会增加启动、调试、数据复制和联调成本。

因此本期保持固定配方、少量业务页面、单实例和一个 Compose 环境，不再拆独立通知或项目服务。如果某个边界后续只产生转发而没有独立规则，需要重新评估该边界，而不是为了保留服务数量继续增加层次。

### 为什么区分预算基准与预算影响结果

既有预算基准属于外部只读数据。重新计算得到的预计成本和预算差额是本系统的派生结果，应保存到自己可写的存储，不能通过改写基准来让预算跟随报价变化。

PostgreSQL 用 schema 隔离数据所有权，是保留两库同时控制部署数量的选择；它仍共享数据库故障和资源竞争范围，不等于每服务一个独立数据库。

### 为什么前端只呈现权威结果

报价、成本和毛利的规则集中在后端，可避免两套算法在舍入、边界条件和版本方面发生分歧。React Query 管理远端数据缓存，SignalR 通知哪些数据需要刷新；两者都不成为最终金额的依据。

这样会牺牲即时本地计算反馈，所以用保存中、计算中、完成/失败状态说明实际进度。先保证结果一致，暂不增加前端计算引擎。

### 为什么先做宿主和环境检查

T01 先确认版本、端口、服务启动和数据库权限，便于把环境问题与之后的业务问题分开定位。健康检查只证明宿主可用；领域模型和业务正确性仍需 T02 之后的测试验证。

Docker Compose 满足本期的本地服务编排需求。Kubernetes、云与鉴权会增加独立工作量，并不改变当前报价计算规则，所以不纳入两周交付。
