## 项目目标与边界

- 约两周完成建筑 ERP 的核心报价流程：报价编辑、成本组成、预算比较、毛利、实时更新。
- 两个业务入口：修改报价数量/销售价；修改资源成本价并传播到受影响报价。
- 保留独立的 Sales、Library、Compositions、Budget 服务，逐个实现，控制业务规模。
- 使用 .NET 8、React/TypeScript/React Query、Clean/Hexagonal 原则、DDD、CQRS、MediatR、MassTransit/RabbitMQ、PostgreSQL、SQL Server 只读访问、SignalR 和 Docker Compose。
- 本期不做 Kubernetes、上云、CI/CD、鉴权/权限、Redis、多实例、主从复制、Event Sourcing、Saga、自动定价或其他 ERP 模块。
- 固定资源配方通过种子数据初始化；业务金额由后端统一计算。具体公式、数据归属和消息版本见架构决策。
- 采用中性的产品和工程说明，只陈述实际能力与计划，不写个人用途，不把未实现功能描述为已交付。

## 技术深度

| 范围 | 本期要求 |
| --- | --- |
| Clean / 六边形 | Sales 保留 Clean 四层；Compositions 明确按六边形的输入/输出端口与适配器组织；Library、Budget 延续简单分层；共同遵循依赖向内，不叠加两套框架 |
| DDD | 从 Quote 聚合、QuoteLine 实体、Money / Quantity 值对象和业务约束开始 |
| CQRS + MediatR | 命令与查询在代码层分开；MediatR 只做进程内分发 |
| 微服务与事件 | 实际跨进程发布/消费；基本重试、去重、旧结果保护和可定位的失败 |
| EF Core / 双库 | PostgreSQL 持久化报价及结果；SQL Server 读取预算基准；不跨服务表访问 |
| React Query / SignalR | 请求和缓存服务器数据、通知后刷新、断线补读、可见的编辑冲突 |
| C# 基础 | 接口、DI 生命周期、async/await、LINQ、decimal 等随对应代码解释，不额外扩展成独立工程 |
| 质量 | 关键业务规则单测与必要集成检查；宿主健康检查不等于业务验收 |
| Outbox | 理解数据库提交与消息发送之间的故障窗口，列为可选增强，不阻塞核心流程 |

特别区分：CQRS 的命令/查询分离不要求不同数据库。PostgreSQL Vente 与 SQL Server Budget 是不同业务数据源，不是同一份报价数据的一写一读副本。RabbitMQ 与 MediatR 的通信边界也不同。

## 推进节奏

1. 先解释当前小步骤解决的业务问题、设计原因和代价。
2. 看相关目录、类或调用路径，用“修改报价数量”这样的具体例子串起来。
3. 用户进入该步骤的实现后，只完成这一小段代码和必要验证。
4. 说明改了哪里、运行结果、尚未实现什么，然后再进入下一轮。

设计思路与代码同样重要，不能一次把整套系统自动做完。“继续”默认指下一项已讨论的小步骤，不代表清空全部 TODO。询问概念、要求解释骨架或整理上下文时，不自行推进业务代码。

在进入首个领域模型前，先介绍已经创建的 Sales 四层项目和实际引用方向。推荐顺序：骨架与依赖 → 一个最小业务模型 → 一个修改命令 → 一个查询 → 数据库 → 页面 → 跨服务事件。每项可以继续拆小，不要求在一轮完成整个 T02。

先完成 Sales 的一个 Clean Architecture 用例；到 T04.3 / T05 再介绍并实现 Compositions 的六边形边界，与 Sales 对照解释。区别体现在业务入口、外部能力接口及适配器职责，不只是目录改名；不提前重建 Sales，也不增加服务或业务范围。设计理由、映射与验证方式见架构决策第 8 节。
